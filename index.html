Module 1 · 在线设备管理

设备结点与有序规则

// 设备信息（数据域）
struct Device {
    char      id[16];   // 设备ID（字符串）
    int       type;    // 0温度 1压力 2振动
    int       prio;    // 优先级 1~5，越小越高
    long long lastTime; // 最近上报时间戳
};

// 带头结点的单链表结点
struct Node {
    Device  data;
    Node*   next;
};

排序规则（双关键字）

先比优先级升序；优先级相同时，再按设备ID字典序升序。注册时插入即有序，所以遍历、统计都无需再排序。

支持的操作

注册设备注销设备 查找设备遍历显示 统计

注册时校验优先级范围 1~5，并检查设备ID是否重复；注销按设备ID定位后摘链。

模块1 · 在线设备管理
模块一的结点一共四个字段。这里的关键是排序规则：两个关键字，优先级优先，优先级相同再看设备ID的字典序。为什么要用带头结点的单链表？因为插入时我们要定位到新结点的前驱，头结点可以让“插到最前面”和“插到中间”两种情况统一处理，不用特判。

Module 1 · 核心实现与测试

插入即有序：一次扫描找到插入点

// 找到第一个"应排在新结点之后"的结点 cur
Node* pre = head;
Node* cur = head->next;
while (cur != NULL && shouldPrecede(cur, fresh)) {
    pre = cur;
    cur = cur->next;
}
fresh->next = cur;   // 新结点插到 cur 之前
pre->next   = fresh;
count++;             // 维护总数

// 双关键字比较：优先级升序，同级按ID字典序
bool shouldPrecede(Node* a, Node* b) {
    if (a->data.prio != b->data.prio)
        return a->data.prio < b->data.prio;
    return strcmp(a->data.id, b->data.id) < 0;
}

模块1 · 核心实现与测试
核心就这个 while 循环：从表头开始扫，只要当前结点应该排在新结点前面，就继续往后走；一旦遇到不该排在前面（也就是应该排在新结点之后）的结点，就停在它前面插入。右边是实际运行输出：注意第 3、4、5 行，三台设备优先级都是 3，ID 是 T001、T003、V001，严格按字典序排列，说明双关键字比较是对的。

Module 2 · 控制指令撤销

链式栈：栈顶就是最近下发的指令

指令#5 · V001 · 更新固件版本栈顶
指令#4 · T003 · 校准压力传感器
指令#2 · T002 · 调整温度阈值45
指令#1 · T001 · 提高采样频率栈底

压栈用头插法，出栈删首结点 —— 两个操作都是 O(1)。

指令结点

编号（自增整数）· 目标设备ID · 指令内容 · 下发时间戳

五个操作

下发指令（压栈）撤销最近（弹栈） 查看最近（读栈顶）撤销全部（清空） 查看历史（不破坏栈）

为什么用链式栈而不是顺序栈？指令条数事先未知，链式栈按需分配、不存在扩容和溢出的问题；而且所有操作都发生在栈顶，正好是链表的头部。

模块2 · 控制指令撤销
模块二用链式栈。左边是栈的示意：栈底是最早下发的指令#1，栈顶是最近的指令#5。“撤销最近”就是弹栈，天然就是 O(1)。选链式栈而不是顺序栈，是因为指令条数事先不知道，链式结构按需分配，不用担心溢出。

Module 2 · 关键难点

不破坏栈结构，输出栈底 → 栈顶

方法一 · 递归回溯

递归深入到栈底，在回溯的路上依次输出。

  • 代码最简洁，不需要额外的数据结构
  • 但递归深度等于指令条数，栈帧开销大
  • 指令很多时有递归过深的风险

方法二 · 辅助栈（本实验采用）

先把主栈元素逐个弹入辅助栈，次序恰好反转。

  • 再从辅助栈逐个弹出并输出，同步压回主栈
  • 两轮倒换之后，主栈完全恢复原状
  • 思路直观、无递归风险；代价是 O(n) 辅助空间
// 第一步：主栈 → 辅助栈，弹出次序被反转
while (!mainStack.Empty())  auxStack.Push(mainStack.Pop());

// 第二步：辅助栈逐个弹出输出，同时压回主栈（栈序复原）
while (!auxStack.Empty()) {
    Command c = auxStack.Top();
    Print(c);                 // 输出：栈底 → 栈顶
    mainStack.Push(auxStack.Pop());
}                            // 结束：主栈元素与顺序完全复原
模块2 · 查看指令历史
这是模块二最有意思的一个点。题目要求“在不破坏栈结构的前提下”输出从栈底到栈顶的全部指令。如果直接反复弹栈输出，指令就全丢了。我用了任务书提示的辅助栈方法：先把主栈全部弹进辅助栈，次序就反过来了；再从辅助栈逐个弹出输出，同时压回主栈，两轮之后主栈完全复原。递归也能做，但指令多的时候有递归过深的风险，所以选了辅助栈。

为什么用 count 计数器？只用 front 和 rear 时，队满与队空的判断条件相同，会出现歧义；加一个 count 后，count = 0 即空、count = 50 即满，彻底消除二义性。

Module 3 · 核心实现与测试

队满时：先丢弃最旧，再让新数据入队

bool EnQueue(DataPacket p) {
    bool dropped = false;
    if (count == MAX) {          // ① 队满：先出队丢弃最旧
        dropped = true;
        DataPacket old = data[front];
        front = (front + 1) % MAX;
        count--;
        PrintDiscard(old);      // 提示被丢弃的数据
    }                            // ② 计数器腾出一格后再入队
    data[rear] = p;
    rear = (rear + 1) % MAX;
    count++;
    return dropped;             // 调用方据此提示“已丢弃最旧”
}

顺序不能颠倒：先判断、先出队，再入队 —— 否则新数据会越界覆盖，旧数据的序列号也会丢失。

这是入队的核心逻辑，顺序很关键：先判断队满，满了就先出队把最旧的丢掉、count 减一，腾出一格，然后再把新数据写进 rear 的位置。如果颠倒了顺序——先写再判断——新数据就会越界覆盖，旧数据的序列号也丢了。右边是真实输出：连续收了 55 条，序列号 6 到 10 被依次丢弃，缓存稳定在 50/50，所以恢复后补传的起点正好是序列号 11。

Complexity · 时空分析

时间复杂度与优化方向

模块操作 时间复杂度改进思路
设备管理注册（有序插入）O(n) 先查哈希索引判重，再定位插入点
设备管理注销 / 查找O(n) 按设备ID建哈希索引，降至平均 O(1)
设备管理遍历显示 / 统计O(n) 注册与注销时维护类型计数，统计降为 O(1)
指令栈下发 / 撤销最近 / 查看栈顶O(1) 头插头删，已是理论最优
指令栈查看指令历史O(n)　辅助 O(n) 改用带尾指针的双向链表或递归，省去辅助空间

复杂度分析
这张表把全部操作过了一遍。绿色的 O(1) 说明栈和队列的操作已经是理论最优了，不用改。真正的问题是设备管理：注册、注销、查找都要从头扫一遍链表，最坏是 O(n)。改进思路就是加一层哈希索引，把设备 ID 映射到结点位置，查找和判重就能降到平均 O(1)。另外统计也可以优化——在注册和注销的时候顺便维护三个类型计数器，统计就直接读计数，不用再遍历。

Discussion · 思考题

工业场景为什么常用循环队列，而不是链式队列？

循环队列 · 优势

  • 内存预分配 —— 定长数组一次分配到位，运行期不再申请与释放，无堆碎片、无分配失败风险
  • 缓存友好 —— 元素物理连续，入出队只移动下标，CPU 预取命中率高
  • 实时性可预期 —— 恒为 O(1) 且没有动态分配的不确定延迟，最坏执行时间可分析
  • 天然过载保护 —— “满则丢弃最旧”，正好契合传感器“保新弃旧”的业务需求
  • 实现简单可靠 —— 只需数组加几个计数器，没有指针错误风险

链式队列 · 短板

  • 每次入队、出队都要动态分配与释放结点，网关常年不间断运行，堆碎片化风险高
  • 结点散布在堆中，访问必须沿指针跳转，缓存命中率低，数据量大时性能差距明显
  • 分配耗时不确定，难以给出最坏执行时间的保证，不利于硬实时场景
  • 容量没有上限，还需要额外设计一套丢弃策略来处理过载
  • 指针维护出错（悬空、泄漏）的排查成本高

在容量上限可以预先确定的工业场景中，循环队列在可靠性、性能与实时性上都优于链式队列 —— 这正是它被广泛采用的原因。

问题讨论
思考题问的是：工业场景为什么常用循环队列而不是链式队列？提示给了三个角度——内存预分配、缓存友好性、实时性。我按这三个角度回答：第一，循环队列用定长数组一次分配，运行期不再动态申请，没有堆碎片；第二，它的元素在内存里是连续的，访问就是移下标，缓存命中率高，链式队列要靠指针跳，缓存不友好；第三，它的入出队耗时恒定、可预测，满足硬实时要求。另外还有两点补充：定长队列天然就能实现“满则丢最旧”，这正好是传感器数据缓存的需求；而且实现简单，不容易出指针错误。
